# Лента и комнаты

Основной источник требований — [`docs/contracts/discovery-v1.md`](docs/contracts/discovery-v1.md), а сценарии экранов — [`docs/design/feed.md`](docs/design/feed.md). Этот файл описывает только текущую клиентскую заглушку.

## Границы реализации

```text
PartyScreen → PartyViewModel → PartyRepository (domain)
                                 ↑
                       MockPartyRepository (data)
```

Одно устройство использует `getFeedItems` и не создаёт комнату. Комната использует единый snapshot `PartyRoom`, приглашение `srastem://party/{roomId}` и `StateFlow` для имитации обновлений нескольких клиентов. Mock добавляет демонстрационного удалённого участника, чтобы можно было увидеть изменение прогресса и результата без сервера. Состояние живёт только в процессе приложения; связь двух физических устройств эта заглушка не обеспечивает.

События ленты берутся из общего `EventRepository`: карта, афиша и карточки свайпов сохраняют один ID. Для места используется локальный демонстрационный каталог. Выбор большинства требует строго больше половины участников; если несколько карточек прошли порог, выбирается карточка с большим числом лайков, затем более ранняя в выдаче.

## Настоящая синхронизация

Handoff задаёт long polling, а не WebSocket: `GET /v1/rooms/{id}?afterVersion=…&waitSeconds=25`. Обновлённый snapshot возвращает `200`, тайм-аут — `204` без тела, истёкшая сессия — `401`. Клиент отменяет ожидание при уходе с экрана и повторно читает комнату при возвращении. Контракт также задаёт `POST /rooms`, приглашения, запуск раунда, голосование, завершение прохода, строгий порог большинства, лимит 20 карточек и срок комнаты 30 минут.

Mock не реализует HTTP-статусы, идемпотентность, стабильные курсоры, восстановление после перезапуска или скрытие чужих голосов на wire-уровне. При подключении стенда нужно добавить data-адаптер к `PartyRepository` и оставить доменные модели и `PartyViewModel` независимыми от DTO/транспортных типов.
