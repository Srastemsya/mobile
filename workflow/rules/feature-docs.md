# Документация фич (FEATURE.md)

Применяется при создании или изменении фичи в мобильном приложении. В корневой директории каждой фичи (`shared/src/commonMain/.../<feature>/`) обязан лежать `FEATURE.md`. Агент читает его, чтобы понять контекст, вместо чтения всего кода фичи.

```
presentation/… или <feature>/
├── FEATURE.md          ← документация фичи
├── domain/ …
├── data/ …
└── presentation/ …
```

## Порядок работы агента

1. Перед работой с фичей — прочитать её `FEATURE.md`, затем `FEATURE.md` связанных фич.
2. При добавлении или изменении функциональности — обновить `FEATURE.md` в том же изменении: новые use cases, endpoints, зависимости, сценарии.
3. Новая фича без `FEATURE.md` не проходит ревью; Developer проверяет наличие и актуальность файла перед сдачей пакета.

## Обязательные секции

1. **Краткое описание** — что делает фича и зачем, 2–3 предложения.
2. **Бизнес-логика** — правила и сценарии без технических деталей (лимиты, условия, порядок шагов).
3. **Архитектура** — по слоям, с конкретными именами:
   - Domain: use cases с одной строкой назначения, модели;
   - Data: репозиторий, API endpoints, DTO;
   - Presentation: ViewModel, поля State, варианты Event.
4. **Зависимости** — «Использует» и «Используется в», относительными ссылками на `FEATURE.md` соседних фич.
5. **Особенности реализации** — подводные камни, платформенные отличия Android/iOS, известные ограничения, обходные пути.

Опционально: API reference с примерами запросов и ошибок, state machine, список экранов и компонентов, тестовые сценарии.

## Правила написания

- Кратко и конкретно: имена классов и методов, а не «есть какой-то use case»; без вводных рассуждений.
- Актуальность: документация меняется вместе с кодом, deprecated помечается.
- Указывать ссылки на спецификацию (`docs/specs/*`) и описание дизайна (`docs/design/*`) фичи, если они существуют.
- Связи между фичами — относительными ссылками: `[Профиль](../profile/FEATURE.md)`.
