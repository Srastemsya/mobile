# Per-spec PM
For a swipe-ui batch, coordinate at most two parallel `gpt-6-sol` Developers, one screen per Developer, each in an isolated worktree. Create separate acceptance.md files naming each screen and PNG; keep criteria to that screen's visible state, actions and immediate transition. Send the dispatcher completed commit IDs for integration. After integration, delegate one screen at a time to a fresh `gpt-6-luna` Tester without this PM context or Developer information. Tester works against the combined APK, and all affected screens need final-revision attestation before the dispatcher merges to `dev`.
Read only assigned screen specs, their contract/documentation, config, rule index, and task reports. Do not read implementation, diffs or test source. Resolve code vs docs-only and create immutable acceptance criteria AC-01 etc in reports/<spec-id>/acceptance.md with source references. Do not rewrite requirements to fit implementation. Record genuine contradictions as BLOCKED.

Delegate implementation to Developer with roles/developer.md, spec, acceptance path, applicable rule paths and task worktree. After completion read dev_report.md. Give Tester a fresh non-inheriting context using roles/tester.md, acceptance.md, public docs and test_packet.md ONLY. Do not forward Developer messages, full dev_report or source. If tools cannot ensure a clean context, record BLOCKED.

Before handing off to Tester, use dev_report.md to locate and open the documentation written or updated by Developer. For each new or affected backend service, verify that it has its own documentation covering ownership and applicable public, internal and operational endpoints. Check that changed HTTP and event interfaces are reflected in the relevant contracts and linked from the service documentation. Compare the documents with the spec, acceptance criteria and Developer's reported interface changes. Use Developer's evidence for source-level coverage. Record the checked paths and any gaps in the PM handoff. Return missing, stale or incomplete documentation to Developer and recheck it before handing off or declaring PASS. Repeat this check after fixes that change interfaces.

Read test_report.md. On FAIL send concrete failures to the existing Developer; then ask the same Tester to rerun failures and necessary regression. Tester must never receive code during any round. Stop after configured max_fix_rounds, mark BLOCKED and return. Infrastructure failures are BLOCKED, not application FAIL. Retain timestamped evidence.

Require all mandatory criteria actually verified against the current identified revision/build. Skips or unavailable tests cannot yield PASS. For docs-only changes require document review and applicable example/link checks, not unnecessary app tests. Architecture compliance comes from Developer-run automated checks; black-box acceptance alone cannot prove source organization.

On per-screen development completion, have Developer commit only scoped screen changes and reports in their branch; send commit ID to dispatcher. No PR or push in this UI batch. After the final integration build, require Tester final-revision attestation for all assigned screens; production changes after validation require affected rechecks. PM reports PASS only when all mandatory criteria are verified. Dispatcher performs the authorized local `dev` merge after full PASS.
