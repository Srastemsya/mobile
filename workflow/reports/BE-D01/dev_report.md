# BE-D01 · Отчёт Developer

Сборка из рабочего дерева на базе `1c336da`. Catalog запущен из образа `sha256:909195b301d5dbd268e5b24d6e135863b5da81a9ddda35a115bcf5941b68cd21` в Compose `srastemsya-be-d01` на `127.0.0.1:18082`.

- Миграция 2 создаёт таблицы PostgreSQL сервиса catalog. Identity и swipes используют собственные БД. Каталог не обращается к чужой БД или внутреннему HTTP. Identity передаёт актуальный статус сессии и профиля через существующий Redis ACL с доступом на чтение для catalog.
- `CatalogRef` хранится как первичный ключ пары `kind, id`. Открытия, поиск, карта и детали используют одну проекцию карточки. Два маршрута деталей события вызывают одну функцию и читают поля зрителя и вместимость из согласованного снимка PostgreSQL.
- Метаданные Redis имеют TTL и ключ с ревизией PostgreSQL. Триггеры меняют ревизию в транзакции категории, подборки или каталожного объекта. Динамические счётчики и поля зрителя читаются при запросе. Публикация, команды записи и события Kafka отложены до BE-D02.
- Шлюз сохраняет отдельный admin JWT и readiness. Скрипт восстановления уже включает catalog. Compose изолирует имена образов по проекту и публикует только Nginx.
- Синтетические данные создаются только в dev, повторные запуски сохраняют их ключи и время начала. На существующих томах BE-D00 сохраняются исходные случайные ID аккаунтов, поэтому связи тестового организатора и участника документированы для чистого стенда.

- `git diff --check` и компиляция Python — успех.
- `NGINX_PORT=18082 docker compose -p srastemsya-be-d01 -f compose.yaml -f compose.dev.yaml up --build -d --wait` — успех на новом проекте и при повторной сборке. `docker compose ps` — все долгоживущие сервисы healthy, только Nginx с опубликованным портом.

- `docker compose stop catalog-db` и последующее `docker compose start catalog-db` — готовность через Nginx сначала `503 {"status":"error","reason":"db"}`, после восстановления `200 {"status":"ok"}`. В журнале catalog только статус запуска и имя хоста.
