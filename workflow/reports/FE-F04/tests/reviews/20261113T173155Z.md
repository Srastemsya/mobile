# FE-F04 evidence review

The Android run covers the central create → invite → join → eligible start path on two concurrent emulator instances. The updated APK was installed on both and the filter/start/poll path was repeated after the party-size field fix. Screenshot evidence is timestamped by local device date in the filenames; the run record supplies UTC window and build identity. Invite tokens and account credentials were not retained.

## Coverage and gaps

- Covered: blank/whitespace room name, organizer creation/lobby, invite copy confirmation, distinct second-member join, live member count, owner/non-owner start visibility, room filters, 10-candidate start, and guest started-state polling.
- Partial only: existing-member rejoin was observed before expiry. The required post-expiry existing-member path was not run.
- Blocked: live new-user expiry and post-expiry rejoin because the 30-minute TTL wait was excluded. A synthetic unknown token produced “Комната не найдена”; it is not equivalent to `INVITE_EXPIRED`.
- Unverified: HTTP idempotency-key stability and cancellation of long polling on leaving the lobby cannot be established from the UI-only black-box surface used here.

## Contract and visual mismatches

- Initial build exposed an editable room `Человек` field although the public room-filter spec says participant count is normalized by the server and hidden. Updated APK omitted it and passed the retest.
- Figma invitation/copy references place invite information and copied feedback in an inline card with avatar group; the app separates the invite route and uses generic member labels. The create button text also differs. AC-07 is reported FAIL.
- The FE-F04-specific design section and feature documentation are current, but the `docs/design/feed.md` overview matrix still points at superseded 182-series room frames while the current section uses 280-series nodes. AC-08 is reported FAIL.
