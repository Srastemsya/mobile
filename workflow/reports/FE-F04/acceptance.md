# FE-F04 acceptance criteria

Scope: Android only per dispatcher instruction; iOS is excluded. Exercise the Android app against `https://srastemsya.nixbi.ru`; server behavior is outside the implementation scope. Test on `emulator-5554`, app `fefu.prime.srastem/.MainActivity`. Do not use the catalog application. Room creation/invite/lobby and start through room filters are in scope. Room voting and FE-F02 swipe integration after start are deferred to the room specs; do not claim them here.

- AC-01 (F04-01): In the multi-device feed flow, organizer can enter a room name and create a room. Blank/whitespace-only names are rejected. Creation enters an organizer lobby showing the room name and one connected creator. Sources: `docs/specs/feed-v1/implementation.md` FE-F04 steps 1–2; `docs/contracts/mobile-api.md` BE-04; `docs/specs/feed-v1/acceptance.md` F04-01.
- AC-02 (F04-01): Organizer can issue an invite and copy its URL; UI visibly confirms the copied state. A second device/user following that URL joins the same room. Organizer lobby reflects member-count increase without manual refresh, and shows the joined member. Sources: implementation FE-F04 step 2; acceptance F04-01; mobile API BE-04; Discovery v1 room invite and long-poll contract.
- AC-03 (F04-01): Start control is available only to organizer and enabled only when at least two members are connected. A non-owner sees no start control. This scope verifies eligibility/visibility only; downstream room voting and swipe navigation are deferred. Sources: implementation FE-F04 steps 3–4; acceptance F04-01; mobile API BE-04.
- AC-04 (F04-02): A new user following an expired invite receives a clear expired-link message and direction to request a new link; the application remains usable. Sources: implementation FE-F04 step 3; acceptance F04-02; Discovery v1 `INVITE_EXPIRED` contract.
- AC-05 (F04-02): An existing room member reopening the same invite is idempotently returned to the current room lobby, including after invite expiry, per service contract. Sources: implementation FE-F04 step 3; acceptance F04-02; Discovery v1 invite contract.
- AC-06: Creation, invite issuance/join, and room state use the documented HTTP contract and stable idempotency keys on repeatable POST calls; asynchronous member updates stop when leaving the lobby. Source: implementation FE-F04 steps 1–3 and long-poll paragraph; `docs/contracts/mobile-api.md` BE-04; `docs/contracts/discovery-v1.md`.
- AC-07: Screens use existing UI Kit components/tokens and match the creation, invitation, and copied-state references at Figma nodes `280-10707`, `280-10728`, `280-10751`, prioritizing legible, practical layout. Sources: FE-F04 implementation references; design rules; `docs/design/feed.md`.
- AC-08: Feature and frontend screen documentation are present and current for room creation/invitation/lobby behavior. Sources: `workflow/rules/feature-docs.md`; `workflow/rules/design.md`.

Platform restriction: validate Android only; do not claim iOS acceptance. Test room behavior on two simultaneous Android emulator instances/devices if possible; report any unavailable setup as infrastructure BLOCKED, not application FAIL.
- AC-09 (additive FE-F04 launch criterion): Organizer can continue from the eligible lobby into the room variant of FE-F01; its party-size field is hidden because the server normalizes `partySize` to the room membership. Organizer can submit the chosen room filters and start via `POST /rooms/{id}/start`. The room transitions out of `LOBBY`; returned initial round has no more than 10 candidates (or the documented `EXHAUSTED` state with `round=null`). Members receive the started state through lobby long polling. Stop acceptance at the started room state; downstream voting/swipe integration remains deferred to room specs. Sources: `docs/specs/feed-v1/implementation.md` FE-F04 step 4; supplied API archive `docs/contracts/discovery-v1.md` room start/pool clauses and `docs/contracts/mobile-api.md` BE-04; dispatcher direction (pool 10; voting deferred).
