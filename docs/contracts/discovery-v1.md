# Контракт первого релиза «Открытия», свайпов и афиши

Рабочий контракт для параллельной разработки Android, iOS и бэкенда. Базовый путь `/v1`. Имена DTO, Bearer-авторизация, ошибки и идемпотентность наследуются из [мобильного API](mobile-api.md). При расхождении для этих экранов действует этот документ. Каталог, события и комнаты требуют завершённого профиля. Для входа действуют правила ниже.

## Вход и регистрация

[Секция «Рега»](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-9964) · [описание дизайна](../design/auth.md)

| Экран или действие | Запрос и ответ |
|---|---|
| [Телефон](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-9997) или [почта](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-10096) | `POST /auth/challenges` с `{channel: SMS\|EMAIL, destination}` → `201 {challengeId, expiresAt, resendAvailableAt}`. Повторная отправка после таймера — новый POST с новым ключом, старый challenge аннулируется. |
| [SMS-код](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-10020) или [код из письма](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-10119) | `POST /auth/challenges/{id}/verify` с `{code: string}` → `200 Session`. Код состоит из четырёх цифр. При `profileComplete=false` открыть завершение регистрации, иначе открыть «Открытия». |
| [Завершение регистрации](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-10047) | `PUT /me/registration` с `{displayName, birthDate}` → `200 Profile`. Имя после обрезки пробелов содержит 1–100 символов, дата в формате `YYYY-MM-DD` не позже текущей локальной даты. После успеха открыть «Открытия». Текущая сессия получает доступ к защищённым маршрутам сразу. |
| Возобновление и выход | `GET /me` → `200 Profile`. `POST /auth/refresh` с `{refreshToken}` → `200 Session` с новой парой. `DELETE /auth/session` → `204`, отзывает текущую сессию. |

В `dev` доставка SMS и письма замокана. Документированные синтетические контакты принимают настроенный четырёхзначный тестовый код (по умолчанию `0427`). Для остальных контактов dev отвечает `422 VALIDATION_ERROR`. API не возвращает код. Mock-режим вне dev запрещён конфигурацией запуска. VK ID, Яндекс ID и связывание контактов отложены. Телефон нормализуется в E.164, email приводится к нижнему регистру после обрезки пробелов. Один подтверждённый контакт соответствует одному аккаунту.

Для стенда challenge действует 5 минут, повторная отправка через 60 секунд, не более 5 неверных попыток на challenge. Неверный код — `422 OTP_INVALID`, истёкший или заменённый challenge — `410 OTP_EXPIRED`, превышение лимита — `429 RATE_LIMITED` с `Retry-After`. Успешная проверка атомарно погашает challenge. POST принимает `Idempotency-Key` по базовым правилам.

Access token — подписанный JWT с `iss, aud, sub, sid, iat, exp`, TTL 15 минут. Мобильный клиент передаёт его как Bearer. Refresh token — непрозрачная случайная строка, TTL семейства 30 дней. Ротация одноразовая. Повтор с тем же ключом в течение 10 минут возвращает тот же результат, повтор старого refresh с новым ключом отзывает семейство. Сервисы проверяют подпись, срок, аудиторию и актуальное состояние сессии в Redis. Для браузерной сессии JWT передаётся в HttpOnly cookie, изменение состояния требует CSRF. Административные маршруты принимают отдельный admin JWT.

## Открытия и общий каталог

- `GET /home` → `200 {quickCategories, collections, upcoming}`. Все поля — массивы. Карусель использует `collections` в серверном порядке. До выбора алгоритма подборки задаются конфигурацией Владивостока. Местоположение пользователя для запроса не требуется. Пустая выдача возвращает пустые массивы.
- `Collection.filters` передаётся как query в `GET /catalog/search`. Для запроса из подборки `q` можно опустить. Выдача состоит из `CatalogCard`. «Смотреть все» открывает `GET /events`, «Свайпать события» открывает выбор устройства с предвыбранным `kind=EVENT`.
- `GET /catalog/categories` → `{items: Category[]}`. Один справочник для фильтров, карточек и формы публикации. Для формы берутся категории с `EVENT` в `kinds`.
- Один объект имеет один `CatalogRef` во всех выдачах. `GET /catalog/EVENT/{id}` и `GET /events/{id}` дают одинаковый DTO `Event` для одного пользователя. Переход на карту использует `ref` и `location`. `GET /catalog/map` включает опубликованное событие при совпадении границ и фильтров.

## Афиша, публикация и участие

| Операция | Ответ и поведение |
|---|---|
| `GET /events` | `200 {items: CatalogCard[], nextCursor}`. Предстоящие события Владивостока, порядок `startsAt, id`. Фильтры `categoryId, localDate, maxPriceMinor, onlyWithSeats` как в базовом контракте. |
| `GET /events/{id}` | `200 Event` с правами текущего пользователя. При `startsAt <= now < endsAt` фаза `ONGOING`, с `endsAt` — `PAST`. |
| `POST /events` | `201 Event`. Тело `CreateEvent`, обязательный `Idempotency-Key`. `endsAt` в этой версии необязателен на входе, по умолчанию начало плюс 2 часа. В ответе всегда присутствует. `timeZone=Asia/Vladivostok`. |
| `POST /events/{id}/registrations` | Пустое тело и `Idempotency-Key`. `201 {registration, admission}` при новой записи, `200` с тем же DTO при существующей активной записи по новому ключу. Запись разрешена только до начала, для посетителя и режима `REGISTRATION`. |
| `GET /events/{id}/registrations` | `200 {items, nextCursor}`, только активные записи, доступ организатору. |
| `DELETE /events/{id}/registrations/{registrationId}` | `200 {registration, admission}` после снятия и при повторе. Тело запроса пустое. Доступ организатору. |

Название, описание и адрес после удаления пробелов непустые. Координаты и категория валидируются. Для `OPEN` поле `capacity` запрещено, для `REGISTRATION` обязательно целое число больше нуля. Цена в RUB, целое число копеек от нуля. Положительная цена допустима для свободного входа как информационное поле. Платную запись API отклоняет как `422 VALIDATION_ERROR` с `details.fields.price=PAID_REGISTRATION_UNSUPPORTED`. Пустая цена сериализуется как `null`. Обложка необязательна, при указании `coverMediaId` требуется собственная готовая загрузка `EVENT_COVER` по [протоколу медиа](mobile-api.md#be-05--история-отправка-и-вложения).

Успех публикации означает видимость по ID и в новых подходящих запросах афиши, карты и свайпов. Уже выданные пулы сохраняют состав. Сервер выводит владельца из сессии. `OPEN` возвращает `admission: {type:"OPEN"}`. Для записи `remainingCount=capacity-confirmedCount`. `409 EVENT_FULL` возвращает актуальные счётчики в `error.details`. После начала — `409 EVENT_CLOSED`, после снятия своей записи — `409 REGISTRATION_REMOVED`, для владельца или свободного входа — `409 INVALID_STATE`. Для чужого списка или удаления — `403 FORBIDDEN`, для записи из другого события — `404 NOT_FOUND`.

В этом релизе чат передаётся отдельной задачей BE-05. До её подключения `canReadChat=false` и `canPostChat=false` для всех. `viewer.saved` отражает существующее сохранение или `false`, лайк из свайпов его не меняет.

## Свайпы на одном устройстве

`GET /feed/candidates?kind=EVENT|PLACE&categoryId?&localDate?&budgetTotalMinor?&partySize?&cursor?` → `200 {items: CatalogCard[], nextCursor}`. Бюджет в копейках RUB. Для бюджетного фильтра `partySize` обязателен, целое от 1. Цена трактуется как цена на человека. При заданном бюджете неизвестная цена исключается, проверка включительная `price.amountMinor * partySize <= budgetTotalMinor`. `localDate` применим только к событиям. Кандидаты EVENT предстоящие на момент создания выдачи. Для PLACE сервер использует справочник мест.

Пул выдаётся порциями до 20 элементов со стабильным порядком и без повторов. Курсор связан с фильтрами и аккаунтом, живёт 30 минут с первого запроса. При повторе действующего курсора возвращается та же порция. При `409 CURSOR_EXPIRED` клиент предлагает обновить подборку. Если `nextCursor=null`, вариантов больше нет. Свайпы и отмена хранятся на устройстве. Первый лайк открывает результат. Для полного описания результата клиент читает `GET /catalog/{kind}/{id}`.

## Свайпы в комнате

Маршруты `POST /rooms`, выпуск и использование приглашения, `GET /rooms/{id}`, запуск, голосование и завершение используют DTO и пути из [BE-04](mobile-api.md#be-04--подборка-и-комната). Создание комнаты и приглашения возвращают `201`, остальные вызовы — `200`. Для POST обязателен `Idempotency-Key`.

- `POST /rooms/{id}/invites` возвращает `{url, expiresAt}`. Клиент извлекает параметр `token` из ссылки и отправляет `{token}` в `POST /room-invites/join`. Ссылка многоразовая в `LOBBY`, действует 30 минут. Повтор входа существующего участника возвращает текущий snapshot, истёкшая ссылка для нового участника — `410 INVITE_EXPIRED`. Старт и выпуск доступны владельцу, постороннему приватная комната возвращает `404 NOT_FOUND`.
- Для старта нужны минимум два участника. Тело `{filters: FeedFilters}` использует `budgetTotal: Money|null`, в отличие от query одиночной выдачи. Сервер нормализует `partySize` до зафиксированного размера комнаты. Максимум 20 карточек в раунде. При пустом пуле старт возвращает `EXHAUSTED`, `round=null`. Изменение фильтров после старта начинает новую комнату.
- Снимок `Room` содержит только свои голоса. Состав и порядок карточек одинаковы для всех. PUT голоса заменяет решение до завершения своего прохода. Завершение без решения по любой карточке — `409 INVALID_STATE`. После завершения голос менять нельзя. Повтор завершения уже завершившего участника возвращает текущий snapshot. Новый голос в старый раунд — `409 STALE_ROUND`.
- После последнего завершения сервер выбирает вариант со строгим большинством и максимальным числом лайков. При равенстве выигрывает более ранняя карточка в зафиксированном пуле. При отсутствии большинства сразу открывается новый неповторяющийся раунд или `EXHAUSTED`. Клиент также допускает промежуточный `REFRESHING`. В `MATCHED` присутствует `result.winner`, в остальных состояниях `result=null`. При завершении комнаты по тайм-ауту и при исчерпании `round=null`.
- Через 30 минут от старта первого раунда незавершённая комната переходит в `CLOSED`. Потеря соединения состав не меняет, отдельного выхода после старта нет. Клиент получает обновления через long polling.

### Long polling комнаты и приглашения

- `GET /rooms/{id}` без параметров возвращает текущий snapshot сразу. Затем клиент держит один `GET /rooms/{id}?afterVersion=<version>&waitSeconds=25`. `waitSeconds` принимает 1–25, по умолчанию 25 при наличии `afterVersion`. `afterVersion` — неотрицательное целое. Без `afterVersion` указывать `waitSeconds` нельзя.
- При версии больше `afterVersion` сервер возвращает `200 Room` сразу или при первом обнаруженном изменении. Если изменений нет до тайм-аута — `204` без тела. Клиент сразу открывает следующий запрос с последней принятой версией, после сетевой ошибки повторяет с задержкой. Ответы со старой версией игнорируются. Тайм-аут HTTP-клиента — больше 25 секунд.
- Создание приглашения и вступление по ссылке остаются командами POST. Пока ссылка открыта у организатора, long poll в `LOBBY` доставляет обновлённый список участников после вступления. Тем же запросом доставляются старт, свайпы, завершение прохода, следующий раунд и результат. При создании приглашения версия меняется только при изменении публичного snapshot. Сам токен приглашения в snapshot отсутствует.
- Доступ проверяется до ожидания и перед ответом. Просроченная или отозванная сессия даёт `401 SESSION_EXPIRED`, посторонний получает `404 NOT_FOUND` сразу. Клиент прекращает ожидание при уходе с экрана и в терминальном состоянии. После возврата читает свежий snapshot.

## Решения для согласования

Для стенда и фронтенд-моков использовать указанные выше значения. Перед выпуском подтвердить конфигурацию карусели, источники и интерпретацию цен, длительность события по умолчанию, платную запись, срок жизни комнаты и правило равных голосов. Подбор по настроению и уведомления пока без API. Карта как экран, отдельные операции профиля, чат и платежи имеют собственные задачи.
