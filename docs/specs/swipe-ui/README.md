# UI-прогон подбора через свайпы

Новые спецификации описывают **видимую часть** сценария подбора. Текущая логика решений, комнаты и выдачи описана в [feed-v1](../feed-v1/implementation.md); персональные фильтры комнаты — новое требование и [отдельная задача для бэкенда](backend-change-note.md). Один Markdown-файл ниже соответствует одному экрану или одному явно нарисованному состоянию экрана. PNG — прямой экспорт соответствующего фрейма Figma, размер 390 × 844; сравнивать на том же размере viewport с учётом системных inset.

Источник: [экран «Открытия»](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-8318), [кнопка входа](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=403-13366), [секция сценария](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=280-10678), [анимированный прототип](https://www.figma.com/proto/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=301-11452&scaling=scale-down&content-scaling=fixed&page-id=280%3A7618&starting-point-node-id=301%3A11452&show-proto-sidebar=1).

## Общие правила визуальной проверки

- Сопоставить экран целиком: иерархию, тексты, переносы, отступы, размеры и обрезку изображений. Контент карточки динамический; фото и тексты на PNG — эталон компоновки, а не фиксированные тестовые данные.
- Статус-бар и безопасные области платформы учитывать отдельно. Внутренний контент не должен заходить под них. На «Открытиях» нижний таб-бар виден; на экране выбора устройства и дальнейших шагах его нет в экспортированных фреймах.
- Геометрию проверять на эталоне 390 × 844: горизонтальный отступ основных форм 20 px; верхняя панель на экранах выбора занимает x=20…370, y=48…100; область нажатия фильтра 44 × 44 px; в фрейме 04 активная карточка занимает примерно x=27…363, y=190…755. Для других размеров сохранять относительную компоновку и безопасные отступы, без растяжения фото.
- Переходы с жестами проверять записью экрана: карточка следует за пальцем, уходит в выбранную сторону, следующая поднимается из стопки; после завершения анимации остаётся ровно одна активная карточка. Проверить также быстрый повтор жеста, отмену и переключение вида «места/события».
- В [прототипе](https://www.figma.com/proto/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=301-11452&scaling=scale-down&content-scaling=fixed&page-id=280%3A7618&starting-point-node-id=301%3A11452&show-proto-sidebar=1) стартовое состояние «Подгрузка · 0 из 3» сменяется стопкой. Проверены последовательные состояния [01 из 10](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=301-8037), [02 из 10](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=301-8349), [03 из 10](https://www.figma.com/design/khewsPf7b4JVyBwJaCmO43/startap_design?node-id=301-8712): после каждого жеста меняется активная карточка, стопка из трёх визуальных слоёв сохраняется. Числа в именах фреймов — шаги прототипа, а не требование показывать счётчик в UI.
- Не задавать численные длительности, пороги жеста и кривые easing по этим статичным фреймам: их в предоставленных ссылках нет. Для реализации брать интерактивный прототип; точные значения требуют решения дизайна.
- Снимки Android и iOS делать в начальном состоянии каждого шага, после каждого значимого действия и на границе перехода. Если результат отличается от Figma из-за существующей реализации, фиксировать расхождение в UI-отчёте с двумя изображениями и ID этого шага.

## Требует решения

1. Прототип демонстрирует движение карточек, но не даёт здесь однозначных числовых параметров анимации. Их не фиксируем как требование без отдельного решения.
2. Фрейм 13 подписан как фильтры организатора и не показывает состояние фильтров приглашённого, отправку выбора и ожидание остальных. Целевой сценарий требует эти состояния; перед пиксельной приёмкой нужны отдельные макеты. Серверные вопросы перечислены в [отдельной пометке для бэкенда](backend-change-note.md).

## Решения для этого UI-прогона

- После «Свайпать события» показывать выбор режима, затем фильтры с предвыбранными «Событиями».
- Целевой вид карточки — точный фрейм Figma. Кнопки «Нет/Да», счётчик и шкала прогресса из прежней FE-F02 на карточном экране не отображаются; жесты остаются основным управлением. Это решение пользователя для UI-части и не меняет бизнес-логику.
- В комнате каждый участник выбирает фильтры на своём устройстве. Сервер объединяет ответы перед формированием общего пула. Это новое целевое поведение; текущий FE/API контракт описывает фильтры только у организатора. Не считать этот участок готовым к полному UI-прогону до изменения контракта и реализации.
