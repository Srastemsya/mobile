# Спецификация разработки · Комната v2

Обязательное публичное поведение — в [контракте комнаты v2](../../contracts/lobby-v2.md). Применяются [правила проекта](../../../workflow/rules/index.md): архитектура бэкенда, runtime-heal, контракты вместе с кодом, тестирование. Работа ведётся в сервисе `swipes` поверх реализации BE-D03; identity и catalog не меняются. Миграции обратно совместимы: комнаты, созданные до v2, продолжают работать с нейтральными весами.

## Общие требования

- Веса, баллы и производные пула хранятся в PostgreSQL сервиса swipes; Redis — только уведомления версий, как в v1.
- Пересчёт баллов и фиксация пула выполняются в той же транзакции, что переход раунда; конкурентные завершения не создают двух разных пулов.
- Чужие веса не попадают ни в snapshot, ни в журналы. Токены приглашений — по правилам v1.
- Стендовые данные: каталог с категориями минимум трёх типов, достаточный для двух полных раундов пул (> 40 кандидатов), наборы для проверок ничьих и нулевых баллов.
- Новые и изменённые маршруты документируются в контракте v2 в том же изменении.

## BE-L01 · Веса в лобби

[Контракт: «Веса в лобби», «Изменения DTO»](../../contracts/lobby-v2.md#веса-в-лобби)

Участник отправляет набор весов категорий до старта и видит его после переподключения. Реализовать `PUT /rooms/{id}/preferences`: валидация категорий по справочнику catalog (кэшируемому, без синхронного запроса на каждый PUT), диапазон 0–3, полная замена собственного набора, идемпотентность по результату (без изменения — без роста `version`). Отразить `hasPreferences` по участникам и собственные `preferences` в snapshot. Фактическое изменение поднимает монотонную версию и будит long poll. После старта и в терминальных состояниях — `409 INVALID_STATE`, посторонний — `404`. Правила следующего пула по весам и итога при исчерпании в этот пакет не входят.

## BE-L02 · Весовое ранжирование пула

[Контракт: «Построение пула по весам», «Следующий пул»](../../contracts/lobby-v2.md#построение-пула-по-весам)

Старт комнаты строит пул по баллам: эффективный вес 1 по умолчанию, балл — сумма по участникам, нулевой балл исключает кандидата, сортировка по убыванию с тай-брейком порядком Discovery v1, до 20 карточек, фиксация состава и порядка. Новый раунд после отсутствия большинства пересчитывает веса (+1 за лайк категории, потолок 5) и исключает показанные карточки. Выбор большинства остаётся правилом v1. Снимок кандидатов по-прежнему получается одним внутренним запросом к catalog на границе создания пула. Итог при исчерпании в этот пакет не входит.

## BE-L03 · Итог при исчерпании

[Контракт: «Итог при исчерпании»](../../contracts/lobby-v2.md#итог-при-исчерпании)

Исчерпание кандидатов после раунда без большинства завершает комнату лучшим по лайкам вариантом: `MATCHED` с `result.kind=TOP_LIKED`, тай-брейк более ранней карточкой; без единого лайка — `EXHAUSTED`. Подсчёт — по всем завершённым раундам комнаты. Обеспечить идемпотентность перехода при конкурентных завершениях, стабильность терминального snapshot при чтениях и переподключениях, `409 INVALID_STATE` для действий после терминала и неизменность правил `CLOSED` по тайм-ауту. `result.kind=MAJORITY` проставляется и для матчей по большинству (общая миграция поля в этом пакете).
